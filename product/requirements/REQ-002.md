# REQ-002：项目领域迁移——城市服务 → 科室挂号

## 1. Product Definition

将现有项目从“城市服务”领域迁移为“科室挂号”领域。

第一阶段仅完成领域定位、前后台核心文案及语义迁移，复用现有页面结构、城市关联逻辑和核心交互，不引入真实医疗/挂号业务能力。

## 2. User Story

作为项目使用者，我希望当前项目能够以“科室挂号”的业务语义呈现，以便后续在此基础上继续建设城市、科室和医生相关能力。

## 3. 领域映射

| 原项目 | 迁移后 |
|---|---|
| 城市服务 | 科室挂号 |
| 城市服务后台 | 科室挂号后台 |
| 一级分类 | 科室 |
| 二级服务 | 医生 |
| 服务列表 | 医生列表 |
| 服务管理 | 医生管理 |
| 城市 | 城市 |

## 4. 后台要求

### 项目定位

- 后台核心标题、页面标题和相关导航统一使用“科室挂号”语义。

### 层级

- 城市继续作为顶部下拉选择项。
- 左侧导航由“一级分类”迁移为“科室”。
- 右侧列表由“二级服务/服务列表”迁移为“医生/医生列表”。

### 既有能力

继续保留现有：

- 城市切换
- 城市与一级层级关联
- 一级层级与二级层级关联
- 分类编辑/删除能力
- 二级层级列表展示
- 排序
- 批量发布
- 发布后的前台联动

> 现有“一级分类有二级服务时禁止删除”的规则，在新领域中对应为“科室存在医生时禁止删除”。

## 5. 前台要求

- 页面核心定位从“城市服务”迁移为“科室挂号”。
- 城市支持切换。
- 一级分类展示语义改为“科室”。
- 二级服务展示语义改为“医生”。
- 保持当前页面整体结构和核心交互。

## 6. 命名规范

### 用户可见文案

统一使用：

- 城市服务 → 科室挂号
- 一级分类 → 科室
- 二级服务 → 医生
- 服务列表 → 医生列表
- 服务管理 → 医生管理

### 技术实现

不得执行无差别字符串替换。

需要根据实际代码判断：

- UI 文案是否迁移
- 业务变量是否迁移
- API 字段是否保持
- 数据库字段是否保持
- 通用组件名称是否保持

## 7. 本阶段明确不做

- 不增加医院字段
- 不增加医生头像
- 不增加医生职称
- 不增加医生擅长
- 不增加排班
- 不增加号源
- 不增加挂号状态
- 不增加医生详情页
- 不接入真实挂号系统
- 不重新设计数据模型
- 不改变城市数据结构

## 8. 验收标准

### 后台

- [ ] 后台核心定位显示“科室挂号”
- [ ] 一级分类统一展示为“科室”
- [ ] 二级服务统一展示为“医生”
- [ ] 服务列表统一展示为“医生列表”
- [ ] 城市下拉选择正常
- [ ] 城市与科室关联正常
- [ ] 科室与医生关联正常
- [ ] 科室编辑正常
- [ ] 科室无医生时可以删除
- [ ] 科室有医生时禁止删除
- [ ] 排序正常
- [ ] 批量发布正常

### 前台

- [ ] 核心定位显示“科室挂号”
- [ ] 城市可以切换
- [ ] 科室展示正常
- [ ] 医生展示正常
- [ ] 城市切换后对应科室/医生数据正常

### 范围控制

- [ ] 没有新增本需求范围之外的医生业务字段或功能
- [ ] 没有因为领域迁移修改不必要的底层数据结构

## 9. 产品结论

REQ-002 是一次低风险的领域迁移，第一阶段应优先验证“城市 → 科室 → 医生”的产品表达和现有系统骨架是否成立。

迁移稳定后，再将医生业务能力作为独立需求进入新的 AI Native 研发周期。
