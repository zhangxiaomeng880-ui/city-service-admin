# REQ-002 Research：城市服务 → 科室挂号

## 1. Research 目标

评估现有项目从“城市服务”迁移为“科室挂号”的可行性，并明确哪些内容属于领域文案迁移、哪些内容属于业务模型变化。

## 2. 当前 Repository 状态

当前 Repository 已建立 AI Native 产品资产，包括 Requirement、Research、Product、Design、Planning 等目录与文档；但目前未发现实际前端应用代码（如 `package.json`、`src/`、页面组件、API 或数据模型）。

因此，本轮 Research 可以确认产品领域映射和迁移边界，但暂不能对真实代码中的引用进行逐项扫描。

## 3. 领域映射评估

| 当前领域 | 迁移后领域 | 判断 |
|---|---|---|
| 城市服务 | 科室挂号 | 迁移 |
| 城市 | 城市 | 保持 |
| 一级分类 | 科室 | 迁移 |
| 二级服务 | 医生 | 迁移 |
| 服务列表 | 医生列表 | 迁移 |
| 服务管理 | 医生管理 | 迁移 |
| 城市选择 | 城市选择 | 保持 |
| 城市与分类关联 | 城市与科室关联 | 逻辑保持，语义迁移 |
| 分类与服务关联 | 科室与医生关联 | 逻辑保持，语义迁移 |

## 4. 迁移原则

### 4.1 展示层优先迁移

第一阶段优先迁移用户可见领域名称、页面标题、导航、按钮、空状态、提示文案等。

### 4.2 不做全局字符串替换

`service`、`category` 等词可能同时存在于 UI 文案、代码变量、API 参数、数据库字段和通用技术逻辑中。不能因为领域名称变化就全部替换。

### 4.3 保持现有业务骨架

暂时保持：

`城市 → 一级层级 → 二级层级`

迁移后的业务语义为：

`城市 → 科室 → 医生`

### 4.4 暂不引入医生业务模型

本轮不增加医院、医生职称、头像、擅长、排班、号源、挂号状态、医生详情等真实医疗业务能力。

## 5. 前台迁移范围

需要迁移：

- 页面/模块标题中的“城市服务” → “科室挂号”
- 一级分类展示语义 → 科室
- 二级服务展示语义 → 医生
- 服务列表语义 → 医生列表
- 与上述领域直接相关的空状态、提示和辅助文案

保持：

- 城市切换
- 城市数据来源
- 页面结构
- 当前核心交互

## 6. 后台迁移范围

需要迁移：

- 后台产品名称
- 一级分类 → 科室
- 二级服务 → 医生
- 服务列表 → 医生列表
- 服务管理 → 医生管理
- 与领域直接相关的操作提示和页面文案

保持：

- 城市下拉选择
- 城市与一级层级的关联逻辑
- 一级层级与二级层级的关联逻辑
- 当前排序、编辑、删除、发布等既有能力的交互骨架

## 7. 风险识别

### 风险 1：领域名与数据模型混淆

“医生”不是简单的“服务”同义词。当前仅做领域迁移时，应继续复用现有数据结构；未来增加真实医生信息时，再单独进行数据模型设计。

### 风险 2：代码变量误修改

不能将所有 `service` / `category` 代码标识符直接替换为 `doctor` / `department`。应区分展示文案、业务对象和底层通用模型。

### 风险 3：前后台语义不一致

后台和前台必须使用一致的领域命名，避免后台叫“科室/医生”，前台仍出现“分类/服务”。

## 8. Research 结论

本次领域迁移可行，且适合复用现有项目的信息架构和交互骨架。

建议采用“两阶段迁移”：

**阶段一：领域迁移**

仅完成项目定位、前后台文案和领域语义迁移，保持数据结构及核心交互不变。

**阶段二：业务深化**

在阶段一稳定后，再单独设计真实医生业务模型，例如医生信息、医院、职称、擅长、排班、号源和挂号能力。

当前 REQ-002 可以进入 Product 阶段。Engineering 阶段必须以实际应用代码为依据执行，不能基于假设直接修改代码。
