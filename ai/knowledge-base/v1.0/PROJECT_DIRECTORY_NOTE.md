# V1.0 知识库补充：项目目录与 AI Native 项目运行机制

## 本次补充

本项目当前 Git 仓库为 `zhangxiaomeng880-ui/city-service-admin`。

项目主要目录：

- `ai/`：AI、知识库与 AI 工作流相关内容
- `product/`：Product 产品事项
- `design/`：Design 设计事项
- `engineering/`：工程相关内容
- `src/`：实际前端代码
- `docs/`：项目文档
- `qa/`：测试与质量保障
- `release/`：发布与版本相关内容
- `analytics/`：数据分析相关内容
- `plugin/`：插件相关内容

## 项目层级与资产关系

项目不把 Git 文件夹层级等同于业务层级。业务层级采用：

**项目 → 业务域/模块 → 事项 → 阶段 → 任务 → 执行记录 → 交付资产**

事项通过唯一 ID 与 Product、Design、Engineering、QA、Release、Knowledge 等资产建立关联。

Project Hub 作为统一入口，负责导航、上下文与项目状态展示；当前不建设独立项目管理平台。

## 当前已确认的遗漏

此前项目整理时，对本次项目已经沉淀在 Git 中的目录结构、层级关系及 AI Native 运行机制记录不完整。本文件作为 V1.0 知识库补充，明确记录：

1. 项目目录本身属于项目资产的一部分，应作为 AI 后续理解项目上下文的依据。
2. Product、Design、Engineering、前端代码、知识库/AI 内容需要保持清晰的职责边界。
3. 当前预览页如果展示后台管理界面，不代表整个项目的前台业务被替换为后台；前台与后台应分别作为不同产品界面进行管理。
4. 项目目录导航页面用于从浏览器可视化访问 Git 中的主要项目目录。
5. 项目执行需要记录负责人、参与人、AI 参与情况、开始/结束时间、工作耗时、等待耗时、返工、变更、阻塞、依赖和交付资产。
6. 项目持续迭代的 V1.0 驱动源为竞品、数据、KPI；用户反馈列为待建设能力。
7. 本项目所说的“自闭环”特指自动化执行闭环：发现 → 分析 → 决策建议 → 执行 → 验证 → 学习 → 再执行。
8. 自动检测必须标注来源与证据，至少能够追溯到来源类型、地址/路径、版本/时间范围、原始证据摘要、判断方法和关联事项。
9. AI 执行前需要进行 Context Readiness 判断；缺失关键上下文时不应自行猜测。
10. 自动变更需要保留版本、输入、决策、修改、影响范围和验证结果，重要变更应支持回滚。
11. 项目经验需要进入 Knowledge Base，并进一步沉淀为可复用模板、规则、Workflow、Agent 和失败经验。

## V1.0 业务上下文

本次项目的核心业务模型为：

**城市 → 医院 → 院区 → 科室 → 医生 → 日期/号源 → 挂号**

当前阶段属于能力建设阶段，暂不指定具体提升指标；单院区医院可跳过院区选择。

## 后续维护原则

新增 Product、Design、知识库、开发及测试资产时，应优先归入已有职责目录，避免在根目录重复创建同类内容。若目录职责、业务层级或 AI Native 运行机制发生调整，应同步更新本知识库及对应版本记录。
