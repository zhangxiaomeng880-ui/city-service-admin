# V1.0 → V2.0 复盘总结

## 1. 背景

V1.0 采用项目制，目标是先用真实项目把 AI Native 流程跑通；在持续执行、审计、测试、Preview Self-test、Model Pool、Routing、数据追踪和知识沉淀过程中，逐步发现可复用的结构规律。

V2.0 不再以单个项目的阶段流程作为系统本体，而是把这些经验抽象为标准 AI Project OS。

## 2. V1.0 验证结果

已验证：

- Project → Product → Design → Engineering → QA → Release → Maintenance 的阶段执行方式
- Stage / Phase Agent
- Input / Output / Execution
- Gate 与自动化 Audit
- Preview Self-test
- Git 资产归档
- Model / Tool / MCP / Skill 调用
- Model Pool 与 Dynamic Routing
- 执行记录、消耗和数据资产
- Knowledge Base 与复盘闭环

## 3. V1.0 暴露的问题

1. 项目流程容易与底层能力混为一体。
2. 阶段 Agent 可能重复定义 Capability。
3. 用户、模型、工具、MCP、Skill、Routing 需要成为独立基础域。
4. 没有 UI 时也必须可以主动 Query / Trigger / Execute。
5. 已有资源不能每次重新创建，需要标准复用机制。
6. 项目创建逐项对话会浪费 Token，需要 Template-first。
7. 项目计划不能只靠人工填写，需要配置驱动生成并给出 Confidence。
8. 数据、工作量、问题、Token、成本、路由和执行记录需要统一成为数据资产。
9. 评审需要逐步由自动化 Audit 替代，并保留证据与追踪。
10. 新业务不能不断复制底层机制，必须通过通用 Contract 扩展。

## 4. V2.0 抽象结果

### 基础域

Identity & Access、Resource、Capability、Execution、Runtime Capability Pool、Model、Routing、Governance、Project Management。

### Resource

Project、Requirement、Phase、Milestone、Task、Issue、Asset、Data、Report。

### Capability

Query、Retrieval、Context Assembly、Action。

### Action

Create、Update、Execute、Publish、Terminate、Delete。

### Runtime

Model、Tool、MCP、Skill。

### 执行

Trigger → MEU → Agent / Workflow → Capability → Runtime → Routing → Execution → Validation → Audit → Trace。

## 5. 人机交互演进

V2.0 固化三项原则：

1. **属性图 / AI Asset Tree**：先粗糙展示已有项目资源及属性，让用户快速发现资源。
2. **Template-first**：项目创建使用完整结构化模板，一次性补齐信息，避免逐项对话。
3. **Reuse-first**：需求、设计、技术方案、代码、测试、审计、发布等已有资源优先 Reference / Clone / Fork。

## 6. 项目创建演进

完整 Project Create Template 必须覆盖项目基础、业务、范围、需求、Design、技术、Code、Testing、Release、Version / Iteration、时间、阶段、计划、预算、风险、权限、AI 执行、已有资产、数据追踪和合规安全。

开始/结束时间、阶段配置、预算、风险、范围、需求规模、资源和历史项目数据进入 Planning Engine，自动生成 Project Plan，并计算计划可行性 / Confidence。

## 7. 路由演进

V1.0 的模型选择能力在 V2.0 收敛为统一机制：

```text
User Specified Model
        ↓
Default Model
        ↓
Dynamic Routing
```

用户指定模型失败时提示用户失败；默认模型失败才进入动态路由。Routing Score、Budget、高并发、质量、成本、延迟和全链路追踪成为标准规则。

## 8. 治理演进

原有人工评审 → 阶段自动化 Audit。Audit 不只是 PASS/FAIL，而必须形成结构化 Input、Output、Execution、Evidence、Result、Trace。

## 9. 数据资产演进

V2.0 将工作量、问题数量、解决情况、返工、变更、Model / Tool / MCP / Skill 调用、Token、Cost、Latency、Routing、Test、Audit、Release 等统一作为 Data Asset，使项目运行本身成为可分析、可复盘、可优化的数据资产。

## 10. V2.0 PASS

本次复盘确认 V2.0 Foundation / Open Capability PASS：底层能力边界、数据关系、用户体系、模型工具池、路由、执行、治理、人机交互原则已经闭环。

PASS 的边界是“标准能力已经形成”，不是“API / SDK 已全部实现”。下一阶段进入 API Contract、Schema、SDK、Registry、Runtime Adapter、Routing Engine、Planning Engine 和可视化产品化的落地实现。

## 11. 后续版本原则

V2.0 后继续新增业务时：

- 优先复用已有 Resource / Capability / Runtime。
- 新增能力必须先判断是否属于现有 Contract 的 Extension。
- 不因单一业务重新设计底层系统。
- UI 是能力的产品化 Adapter，不是能力成立的前提。
- API / SDK 是 V2.0 开放能力的标准执行出口。
