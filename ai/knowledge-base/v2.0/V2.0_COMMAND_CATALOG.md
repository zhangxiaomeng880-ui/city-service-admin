# AI Native Project OS V2.0 — Command Catalog

## 1. Purpose

This document defines the standard command entry layer for V2.0. Every exposed capability MUST be discoverable and executable without relying on a UI.

The same command contract is intended to be consumed by:

- Human command / chat interface
- Agent
- Workflow
- API
- SDK
- Tool / MCP adapters
- Future UI

Core flow:

`Query / Retrieval → Context Assembly → Command → Execution → Validation / Audit → Trace → Data Asset`

## 2. Standard action vocabulary

All resource operations use the standard Action vocabulary:

- `Create` — create a resource
- `Update` — modify a resource
- `Execute` — execute a capability or resource action
- `Publish` — make a validated version/configuration effective
- `Terminate` — stop an active execution
- `Delete` — remove a resource when policy permits

A resource does not need to support every Action. Support is determined by Resource Contract, Lifecycle, Action Policy and Permission.

## 3. Runtime capability boundaries

V2.0 MUST keep the following concepts separate and explicitly related:

### Model

The Model provides reasoning, generation or other AI inference. A Model does not become a Tool merely because it is invoked during execution.

### Skill

A Skill is a reusable method / procedure / knowledge-guided execution pattern created and maintained by the platform or project. Skill is not an external execution endpoint.

Lifecycle:

`Skill Create → Validate → Publish → Skill Pool → Agent / Workflow use`

### Tool

A Tool is an executable interface that performs an action against a system, repository, file, data source, environment, test runner, external API, or other execution target.

Typical Tool categories include:

1. **Repository / Code** — repository, branch, commit, file read/write, code search, PR, CI/workflow.
2. **Design** — design file/context, component, export and design-system operations.
3. **Data / Analytics** — SQL, Python, notebooks, data query, validation, visualization and report generation.
4. **File / Document** — file read/search/write, document parsing, generation and conversion.
5. **Web / Retrieval** — web search, URL fetch, retrieval and image search.
6. **Project Management** — project, issue, task, milestone, comment and workflow operations.
7. **Testing** — test runner, API/UI/visual/performance test execution and result collection.
8. **Deployment / Environment** — build, environment, preview, deployment, release and rollback.
9. **Communication / Notification** — message, email, notification and webhook.
10. **AI Runtime** — model invocation, embedding, image/audio generation and other AI APIs when exposed as executable integrations.
11. **Utility** — calculator, parser, formatter, validator, converter and scheduler.

A business capability such as `Audit` or `Test` is NOT itself a Tool. For example:

`Audit Capability → Agent → Repository Tool → Code`

`Test Capability → Agent → Test Tool → Test Runner`

### MCP

MCP is an external capability integration protocol, not a synonym for Tool.

An MCP Server may expose Tools, Resources and Prompts. An MCP-backed Tool is therefore a Tool whose execution is delivered through the MCP integration layer.

### Agent

An Agent organizes Model + Skill + Tool according to the assigned Capability / Workflow. The Agent is responsible for deciding which available resources and execution capabilities are needed within policy; it does not redefine the underlying Tool, MCP or Model contracts.

### Routing

Routing selects an eligible Model / Runtime execution path according to policy. Routing does not replace Agent orchestration.

## 4. Runtime execution relationship

The canonical execution relationship is:

`User / Workflow → Capability → Agent → Routing → Model + Skill + Tool → Execution`

For a native Tool:

`Agent → Tool → Target System`

For an MCP-backed Tool:

`Agent → Tool → MCP Adapter → MCP Server → External System`

The Tool does NOT autonomously decide to call a Model or MCP. The Agent / Workflow / Runtime orchestration determines what needs to be invoked. If a Tool is implemented through MCP, the Tool's adapter invokes the MCP Server according to its registered contract.

Therefore the architecture MUST NOT be represented as:

`Tool → Model → MCP`

The correct conceptual separation is:

- **Model** — think / generate
- **Skill** — provide a reusable method
- **Tool** — perform an executable action
- **MCP** — standardize external capability integration
- **Agent** — organize Model + Skill + Tool
- **Routing** — select the eligible runtime path
- **Audit** — independently inspect the result/process

## 5. Runtime Integration / Adapter Layer

Model, Tool and MCP are extensible runtime assets. V2.0 MUST define how external capabilities enter the common capability pool.

Canonical onboarding flow:

`External Capability → Integration / Adapter → Compatibility Validation → Security / Permission Validation → Health Check → Capability Discovery → Registration → Capability Pool`

### Model onboarding

Model registration MUST support, as applicable:

- Provider
- Model ID / version
- API endpoint
- Authentication reference
- Input / output capability
- Context limits
- Pricing / cost data
- Health status
- Availability
- Capability validation

Model connection must be validated before publication to the Model Pool.

### Tool onboarding

Tool registration MUST support:

- Tool ID / provider
- Endpoint or executable reference
- Input / output schema
- Authentication
- Permission
- Timeout
- Error contract
- Health check
- Cost when applicable
- Capability description

### MCP onboarding

MCP integration MUST support an extensible adapter model rather than hard-coding one MCP Server implementation.

At minimum, the MCP registration contract should be able to represent:

- MCP ID / name / version
- Server endpoint / URL when applicable
- Transport
- Authentication
- Capability discovery
- Tools / Resources / Prompts exposed by the server
- Input / output schemas
- Permission and security policy
- Health check
- Timeout policy
- Error handling
- External cost policy when applicable
- Registration / publication status

MCP onboarding flow:

`MCP Server / Endpoint → MCP Adapter → Protocol Check → Capability Discovery → Schema Validation → Security / Permission Check → Health Check → Register → MCP Pool`

The adapter layer MUST allow additional supported transport, authentication or provider implementations to be added without changing the core Tool / Capability contracts.

### Skill onboarding

Skill is internally created rather than treated as an external provider connection:

`Create → Validate → Publish → Skill Pool`

## 6. Command naming convention

Commands use:

`<resource>.<action>`

Examples:

- `project.create`
- `project.query`
- `resource.tree`
- `requirement.reference`
- `test_case.create`
- `test.execute`
- `audit.execute`
- `model.list`
- `model.update`
- `tool.list`
- `mcp.list`
- `skill.list`
- `routing.execute`

Commands that are discovery-oriented may use a capability-specific suffix such as `query`, `tree`, or `search`; these are mapped to Query / Retrieval capabilities rather than creating a second action vocabulary.

## 8. Generic command contract

Every command MUST expose the following metadata:

```yaml
command_id: <string>
resource_type: <string>
action: <Create|Update|Execute|Publish|Terminate|Delete|Query|Retrieve|Discovery>
description: <string>
permission: <permission expression>
input_schema: <schema reference>
required_fields: []
optional_fields: []
preconditions: []
execution_mode: <sync|async|stream>
output_schema: <schema reference>
error_schema: <schema reference>
trace_schema: <schema reference>
audit_required: <true|false>
```

## 9. Trigger methods

A command can be triggered through multiple adapters while keeping the same underlying contract:

1. **Command** — explicit command invocation.
2. **Natural language** — AI maps user intent to a registered command.
3. **Event** — system event invokes a command.
4. **Schedule** — scheduled execution invokes a command.
5. **UI** — future UI calls the same command/API layer.
6. **API / SDK** — external systems invoke the command contract directly.

UI is therefore an adapter, not a prerequisite for execution.

## 10. Natural-language resolution rule

When a user gives a natural-language instruction:

`User Intent → Query/Retrieval → Resource Resolution → Command Resolution → Permission Check → Input Validation → Execute → Trace`

The Agent MUST prefer existing resources when a reusable resource is available. It should use the AI Asset Tree to expose candidate resources when user selection is needed.

## 11. Project creation command

`project.create` uses the complete Project Create Template.

All standard project fields MUST resolve to a value, but the value may come from:

- User input
- Existing resource reference
- Template default
- AI inference requiring user confirmation
- System-generated value

Project planning inputs include start/end time, phase configuration, budget, risk configuration, scope, resources and historical project data.

The Planning Engine generates an initial project plan and a confidence assessment before final confirmation.

## 12. Execution record

Every executable command MUST create an execution record containing at minimum:

- execution_id
- command_id
- project_id / resource_id when applicable
- actor / agent
- selected model / tool / MCP / skill
- routing decision
- start/end time
- status
- token / usage / cost data when applicable
- input/output references
- issue references
- validation/audit result
- trace_id

These records are project data assets and must be queryable and archivable.

## 13. Error and failure behavior

- User-specified model has the highest priority. If the user-specified model fails, report failure to the user rather than silently switching models.
- Default model failure may enter the configured routing mechanism.
- Routing decisions must be traceable.
- Permission failure, validation failure, precondition failure and execution failure must remain distinguishable.
- Termination must preserve the execution trace.
- External integration failure must identify whether the failure occurred at adapter, authentication, protocol, capability discovery, schema validation, health check, permission, or downstream execution level.

## 14. Command discoverability

The system MUST expose a queryable Command Catalog so that an Agent, developer or user can determine:

- What commands exist
- What resource each command operates on
- What Action it represents
- Required inputs
- Permission requirements
- Expected outputs
- Failure conditions
- Whether audit is required
- Whether execution is synchronous/asynchronous
- Whether the command depends on Model / Skill / Tool / MCP

This document is the human-readable catalog. API/SDK schemas should reference the same command identifiers and contracts rather than defining a second incompatible command system.

## 15. V2.0 PASS boundary

V2.0 is not considered fully PASS until all of the following are available as standardized, executable contracts:

1. Capability discovery and Query / Retrieval.
2. Standard Action vocabulary and Command Catalog.
3. Model Pool with onboarding validation.
4. Tool Pool with onboarding and execution contract.
5. MCP Pool with adapter-based extensible onboarding and validation.
6. Skill creation, validation and publication lifecycle.
7. Agent orchestration of Model + Skill + Tool.
8. Routing policy, score, budget, failure and trace rules.
9. Independent Audit / Validation.
10. Execution Trace and data archiving.
11. No-UI command trigger mechanism.
12. API / SDK-compatible contracts.

## 16. Relationship to V2.0

`V2.0 Capability → Command Contract → Runtime Integration / Adapter → API / SDK → Agent / Workflow / UI / External System`

The Command Catalog and Runtime Integration layer together form the executable bridge between the V2.0 PASS capability foundation and subsequent V3.0 SaaS productization.
