# AI Native Project OS V2.0 — Validation & Retrospective

## 1. 验证定位

本文件是 V2.0 的正式验证台账与后续复盘主文档。

验证原则：

> 以 V1.0 已完成项目及其历史资产副本作为真实验证样本，验证 V2.0 的 Resource、Capability、Command、Runtime、Routing、Execution、Audit、Trace、API / SDK 契约是否能够作用于真实资产。

V1.0 原始资产不修改；V2.0 使用 `ai/knowledge-base/v2.0/resource-pool/v1.0/` 独立副本进行验证。

## 2. 验证状态定义

- **PASS**：已经有可核查的实际执行证据。
- **PARTIAL**：规范和资源已经具备，但实际执行链路或部分依赖尚未完成。
- **FAIL**：实际执行与规范不一致，或能力不可用。
- **BLOCKED**：验证依赖尚未提供，当前无法完成真实执行。
- **N/A**：本轮样本不适用。

不得因为文档已经定义而直接判定 PASS。

## 3. V2.0 验证总体策略

V2.0 采用 **“最小闭环验证 → 项目级验证”** 的两阶段策略。

### 3.1 第一阶段：最小闭环验证

目标不是一次性运行整个 V1.0 项目，而是先证明 V2.0 的底层通用能力能够独立执行。

最小闭环：

`Resource → Query → Retrieval → Context Assembly → Command → Agent → Routing → Model / Skill / Tool → Execution → Audit → Trace`

**Routing 是最小闭环的强制环节，不允许在验证过程中绕过 Routing 直接选择模型或 Runtime。**

第一阶段重点回答：

> V2.0 的 Resource、Capability、Command、Runtime、Routing、Execution、Audit、Trace 是否真正形成可执行闭环？

只有真实执行并产生证据，才允许判定 PASS。

### 3.2 第二阶段：真实项目验证

最小闭环 PASS 后，再使用 V1.0 完整项目资产验证复杂项目能力：

`Project → Requirement → Phase → Task → Asset → Capability → Agent → Routing → Execution → Audit → Report`

项目级验证重点不是重新证明每一个底层能力存在，而是验证：

- 能力组合
- 资源关系
- 阶段关系
- 任务依赖
- 资源复用
- 多步骤执行
- 状态流转
- 返工与再次执行
- 全链路 Trace
- Report 归档

因此，最小闭环 PASS 后，项目级验证主要承担 **组合、复用、关系和边界验证**，不能直接跳过项目验证并宣称整体 PASS。

### 3.3 验证原则

```text
定义
 ↓
命令
 ↓
实际执行
 ↓
执行证据
 ↓
验证结果
 ↓
问题
 ↓
修复
 ↓
再次执行
 ↓
最终结论
```

核心原则：

> **没有执行证据，不判定 PASS。**

### 4.3 自动验证推进规则

V2.0 Validation 默认采用：

**Autonomous Execution + Human Gate**

自动机制负责：

- 读取 Validation Plan
- 读取当前验证状态
- 选择下一最小验证任务
- 执行可用的 Query / Retrieval / Command / Runtime
- 记录 execution / trace / evidence
- 判定 PASS / PARTIAL / FAIL / BLOCKED
- 自动推进到下一项非阻塞任务
- 自动更新验证台账

Human Gate 仅在以下情况暂停：

- 需要业务或架构决策
- 高风险操作（如真实生产发布、删除等）
- 阶段 Gate（例如最小闭环 PASS 后是否进入项目验证）

### 4.4 Routing 强制规则

自动验证机制必须保持与 V2.0 正式 Routing 机制一致，不允许为了验证方便而绕过路由层。

每一次涉及模型 / Runtime 的执行必须遵循：

```text
Execution Intent
 ↓
User-specified Model Check
 ↓
Candidate Pool
 ↓
Eligibility / Constraint Filter
 ↓
Routing Score
 ↓
Selected Runtime
 ↓
Execution
 ↓
Failure Handling
 ↓
Trace
```

规则固定为：

1. 用户指定模型优先级最高。
2. 用户指定模型执行失败时，向用户报告失败，不静默切换其他模型。
3. 默认模型是初始选择，不代表失败后继续固定使用；默认模型失败时进入已配置的 Routing 机制。
4. 动态 Routing 必须考虑质量、低消耗、高并发及路由预算。
5. 低消耗的目标是控制不必要的 Token / Runtime 消耗，**不能以牺牲质量为代价**。
6. 路由预算是高并发场景下的最高消耗约束，不是单个任务的预算。
7. 每次 Routing 必须产生 routing decision trace。
8. Routing 规则、候选池、分值和失败路径必须可追踪、可归档。

## 7. 当前第一轮主要发现

### Finding-001：Command Runtime 尚未真正落地

**现象：** Command Catalog 已经完整定义 `project.query`、`resource.tree`、`routing.execute`、`audit.execute` 等命令，但当前仓库中尚未验证存在一个统一的 Command Runtime，可以接收命令、解析 Contract、执行并返回标准 Trace。

**影响：** V2.0 当前只能证明“命令契约已定义”，不能证明“命令已经可执行”。

**状态：PARTIAL / BLOCKED**

**后续动作：** 建立最小 Command Runtime，至少支持 Query、Retrieve、Tree、Create、Update、Execute、Publish、Terminate、Delete 中的核心子集，并产生标准 execution_id / trace_id。

### Finding-002：Runtime Registry 尚需实际执行验证

**现象：** Model / Tool / MCP / Skill 的接入、校验、注册规则已经定义，但当前缺少统一 Registry + Adapter 的真实运行证据。

**状态：PARTIAL**

**后续动作：** 优先选择一个 Model、一个 Tool、一个 MCP Server、一个 Skill 完成完整 Onboarding → Validate → Register → Execute → Trace。

### Finding-003：独立 Audit 执行尚需验证

**现象：** Audit 已从旧评审机制中独立出来，Command Catalog 已明确 `audit.execute` 和 `validation.execute`，但当前缺少独立 Audit Runtime 的真实执行记录。

**状态：BLOCKED**

**后续动作：** 使用 V1.0 已有项目资产作为审计对象，建立独立 Audit Agent 执行一次端到端审计，验证审计与被审计执行主体隔离。

### Finding-004：自动验证必须经过 Routing

**现象：** 当前可以通过仓库工具读取验证资产，但当前工具环境本身不是 V2.0 Model / Runtime Router，因此不能把工具读取结果冒充 `routing.execute` 的执行证据。

**状态：PARTIAL**

**后续动作：** 最小闭环一旦进入模型 / Runtime 调用，必须首先建立候选池、用户指定模型检查、Eligibility Filter、Routing Score、Selected Runtime 和 routing trace，再执行模型；禁止直接选择一个模型以“方便验证”。

## 9. 为什么采用“两阶段验证”

最小闭环用于证明：

> **V2.0 的底层通用能力真的成立。**

项目验证用于证明：

> **这些能力能够正确组合、复用，并支撑真实项目中的复杂关系。**

因此：

`Minimum Closed Loop PASS ≠ Project Validation PASS`

但最小闭环 PASS 后，项目验证的重点将从“能力是否存在”转向“组合 / 复用 / 关系 / 边界是否正确”。

## 10. V2.0 最终 PASS 条件

V2.0 只有在以下条件全部具备执行证据后才能 PASS：

- Resource 可查询、检索、组装上下文
- Command 可以无 UI 触发
- Model / Tool / MCP / Skill 可以接入并校验
- Agent 可以实际编排 Runtime
- Routing 可以真实选择执行路径
- Execution 可以产生完整记录
- Audit 独立执行并产生证据
- Trace 可查询和归档
- Report 可生成
- API / SDK 可以复用同一 Command Contract
- V1.0 真实项目至少完成一次端到端闭环验证

## 11. 复盘规则

验证期间不得为了得到 PASS 而修改历史证据。

所有缺陷必须保留：

- Finding ID
- 发现时间
- 发现入口
- 预期行为
- 实际行为
- 影响范围
- 根因
- 修复方案
- 修复版本 / Commit
- 再验证结果

最终复盘需要回答：

1. V1.0 哪些实践成功抽象成了 V2.0 能力？
2. 哪些能力只是文档标准，尚未真正执行？
3. 哪些能力需要补充 Runtime？
4. 哪些能力边界需要调整？
5. 哪些能力已经可以复用于新的 Project Type？
6. 哪些问题应进入 V3.0？
