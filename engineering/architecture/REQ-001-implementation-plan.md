# REQ-001 Implementation Plan

## 1. 目标

实现一级分类的编辑和删除能力，并保证「城市 → 一级分类 → 二级服务」关系完整。

## 2. 已确认产品规则

1. 一级分类支持编辑。
2. 一级分类无二级服务时允许删除。
3. 一级分类存在二级服务时禁止删除。
4. 禁止删除时不得删除、解除关联或迁移二级服务。
5. 删除成功后后台分类列表与右侧服务列表状态必须正确刷新。
6. 前台已发布数据不能产生孤儿服务。

## 3. 实施前需要检查现有代码

Engineering Agent 开始编码前必须先确认：

- 一级分类列表组件/页面位置
- 分类数据模型及城市关联方式
- 二级服务与一级分类的关联字段
- 当前新增分类逻辑
- 当前排序逻辑
- 当前发布/批量发布逻辑
- 前台读取发布数据的方式
- 是否已有分类 API / 本地状态管理

本文件不假设上述实现细节已经存在。

## 4. 推荐任务拆解

### TASK-001：一级分类编辑

- 增加编辑入口
- 复用或扩展现有分类表单
- 校验分类名称
- 保存后刷新分类列表
- 保持二级服务关联不变

验收：编辑成功、取消无副作用、刷新后数据保持一致。

### TASK-002：一级分类删除

- 增加删除入口
- 删除前执行关联服务检查
- 无二级服务时展示确认操作
- 删除成功后刷新分类列表

验收：无服务分类可删除；删除后分类不再展示。

### TASK-003：删除业务校验

后端/数据层必须执行最终校验：

```text
删除分类
   ↓
查询该分类是否存在二级服务
   ↓
有服务 → 拒绝删除 + 返回明确原因
无服务 → 执行删除
```

不能仅依赖前端按钮禁用。

### TASK-004：当前选中状态处理

分类被删除后：

- 当前选中分类不存在时重新选择合理的可用分类
- 右侧服务列表不能继续展示已删除分类的数据
- 无分类时展示空状态

具体默认选中策略在实现前结合现有页面逻辑确认。

### TASK-005：发布/前台联动检查

确认分类删除或编辑对已发布数据的影响。

如果当前系统采用“编辑后先保存、再发布”的机制，则后台修改不应未经发布直接改变线上前台；如果当前实现是实时读取，则需要按现有机制处理。

不得在未检查现有发布机制的情况下改变发布行为。

### TASK-006：测试

覆盖：

- 编辑成功
- 编辑取消
- 空名称校验
- 删除无服务分类
- 删除有服务分类
- 删除确认取消
- 删除后当前选中状态
- 城市切换
- 前台已发布数据
- 批量发布相关回归

## 5. 依赖关系

```text
TASK-001 编辑

TASK-003 删除业务校验
        ↓
TASK-002 删除
        ↓
TASK-004 状态处理
        ↓
TASK-005 发布/前台联动
        ↓
TASK-006 测试
```

TASK-001 与 TASK-003 可以并行分析，但实际编码前必须先完成现有数据结构检查。

## 6. 风险

### 高风险

- 删除接口可能误删全局分类，而不是当前城市的分类关联。
- 前后台可能使用不同的数据源，导致删除后状态不一致。

### 中风险

- 当前选中分类删除后的右侧服务状态。
- 发布机制与后台编辑状态之间的边界。

PR 必须关联 REQ-001。

## 8. Planning 结论

REQ-001 已从产品问题转换为可执行的工程任务，但在实际 Coding 前必须读取现有代码并验证上述实现假设。Planning 不直接替代代码审查；如果现有代码与计划不一致，应先更新实施计划，再编码。
