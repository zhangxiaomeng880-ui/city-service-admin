# REQ-001 Design：一级分类编辑与删除

## 1. 设计目标

在不改变现有「城市 → 一级分类 → 二级服务」信息架构的前提下，为一级分类增加编辑、删除能力，并通过明确的风险提示保护分类与服务之间的层级关系。

## 2. 页面结构

当前后台页面保持：

```text
城市下拉
──────────────
左侧：一级分类导航
右侧：二级服务列表
```

本需求不新增城市管理入口，也不改变一级分类作为左侧导航的定位。

## 3. 一级分类操作

建议在一级分类项的操作区域提供：

- 编辑
- 删除

正常状态下不增加额外的视觉层级，避免左侧导航变成复杂的表格操作区。

## 4. 编辑交互

点击「编辑」后，使用轻量编辑态或弹窗编辑分类名称。

建议字段：

- 分类名称：必填

交互：

```text
编辑一级分类

分类名称 [____________]

[取消] [保存]
```

规则：

- 名称不能为空
- 点击取消不产生变更
- 保存成功后左侧分类名称立即更新
- 不改变该分类下已有二级服务的归属

## 5. 删除交互

### 场景 A：无二级服务

允许删除，但需要二次确认：

```text
删除分类？

删除后该分类将从当前城市中移除，此操作不可直接恢复。

[取消] [删除]
```

删除成功后：

- 左侧分类移除
- 若当前正选中该分类，自动选择合理的下一项/第一项
- 右侧服务区域同步更新为空或展示新选中分类内容

### 场景 B：存在二级服务

禁止删除，不进入真正的删除确认：

```text
无法删除该分类

该分类下存在 X 个服务，请先处理关联服务后再删除。

[知道了]
```

核心原则：**不删除服务、不解除关联、不自动迁移服务。**

## 6. 操作状态

| 场景 | 编辑 | 删除 |
|---|---|---|
| 正常分类 | 可用 | 可用/根据服务数量判断 |
| 有二级服务 | 可用 | 禁止删除 |
| 保存编辑中 | 防重复提交 | - |
| 删除提交中 | - | 防重复提交 |

## 7. 前台联动

本需求涉及后台分类数据变化，但不改变前台信息架构。

- 分类编辑：前台展示名称应在发布数据更新后同步
- 分类删除：删除成功后，该城市的前台发布数据不得出现该分类
- 分类下存在服务时禁止删除，因此不会产生无归属服务

具体是否实时同步或需要重新发布，以当前项目既定发布机制为准；Engineering 阶段需要确认实际数据链路。

## 8. 视觉原则

- 左侧导航保持轻量，不做成传统表格
- 操作入口避免长期增加过强视觉权重
- 删除使用危险操作语义，但不制造过度警示
- 弹窗内容明确说明影响对象
- 有关联服务时直接解释“为什么不能删除”，不要只显示“删除失败”

## 9. Design Acceptance Criteria

- [ ] 一级分类能够明确找到编辑入口
- [ ] 一级分类能够明确找到删除入口
- [ ] 编辑状态与左侧导航视觉关系自然
- [ ] 无服务分类删除有二次确认
- [ ] 有服务分类删除被明确阻止
- [ ] 阻止提示包含关联服务数量/原因
- [ ] 删除后左侧及右侧内容状态正确
- [ ] 前台发布链路不产生孤儿服务

## 10. 待 Engineering 确认

1. 当前一级分类操作入口的实际组件和交互实现。
2. 当前分类与城市关联是删除“城市分类关系”还是删除“全局分类实体”。
3. 当前发布机制是否要求分类变更后再次执行发布。
4. 当前选中分类被删除后，默认选中哪一个分类。
